# Sentinel Vault 7.0.0 — permission scopes, call by call

GENERATED by the 7.0.0 scope audit (2026-10-05). Every outgoing Atlassian call in `src/` is listed with the scopes Atlassian accepts for it (the `x-atlassian-oauth2-scopes` of the Confluence v1/v2, JSM and Assets OpenAPI specs, fetched 2026-10-04) and the scope that still covers it after the trim. Where the spec offers alternatives (classic OR granular), either set is enough.

Production 6.11.0 declares 38 scopes. 7.0.0 adds one (`report:personal-data`, the weekly personal-data check) and removes 12: 27 scopes. Calls not covered after the trim: **0**.

## Removed (12)

- `read:confluence-space.summary` — No call needs it; no space or label trigger. Content search with expand=space is covered by search:confluence (live: backup discovery still returns spaceKey/spaceName).
- `read:confluence-props` — Granular-era duplicate: no v1 content-property endpoint is called; every property read/write goes through v2 page/space properties (read/write:page, read/write:space).
- `read:content:confluence` — No v1 call lists it as an alternative that the classic scopes don't already cover.
- `write:content:confluence` — Same: classic write:confluence-content stays and covers labels, pageTree delete, restrictions.
- `write:attachment:confluence` — Granular alternative of the v1 attachment upload/update calls; classic write:confluence-file (+ write:confluence-props for the un-trash PUT) stays and covers them.
- `read:comment:confluence` — The app only CREATES footer comments (v2 POST /footer-comments needs write:comment:confluence, kept); it never reads comments.
- `read:content.property:confluence` — No v1 content-property call; v2 properties use read:page / read:space.
- `write:content.property:confluence` — No v1 content-property call; v2 properties use write:page / write:space.
- `read:content.restriction:confluence` — The one restriction read (v1 GET /content/{id}/restriction) is covered by read:confluence-content.all.
- `write:content.restriction:confluence` — The one restriction write (v1 PUT /content/{id}/restriction, backup page) is covered by write:confluence-content.
- `read:content.metadata:confluence` — Granular alternative of the sync contentbody/convert call; read:confluence-content.all stays (live: convert answers 200 after the trim).
- `read:content.permission:confluence` — Granular alternative of v1 POST /content/{id}/permission/check; classic read:confluence-content.permission stays.

## Proposed for removal on 2026-10-04 but KEPT

- `read:confluence-content.summary` — REQUIRED by the five product triggers (page created/updated, attachment updated/trashed/deleted): Forge's events reference says page and attachment events "require the OAuth scope `read:confluence-content.summary`", and `forge lint` fails with `permission-scope-required` on all five when it is removed (measured 2026-10-05). Removing it would have silently switched off seal enforcement.
- `read:label:confluence` — `forge lint` maps the page-label read (`/wiki/api/v2/pages/{id}/labels`, src/server/infra/labels.js:20-21) to `GET /labels` and fails without it, while the v2 spec lists only read:page:confluence. Ambiguous, so it stays.

The reds that were green are event latency, not scopes. gate-revert, revert-destructive and the restore journey wait for Confluence's page-updated / attachment-trashed events, and on dev today those arrived 30 s to 10 min late in bursts (the issue in docs/FORGE-SUPPORT-EVENT-LATENCY-2026-09-15.md). Proof: (1) the [PAGE-EVENT] first-line log shows the handler simply had not been invoked yet when the specs gave up, then the events landed in bursts; (2) an A/B with the FULL 39 scopes redeployed on the same install failed both too: the restore journey on the identical assertion (the trashed event had not landed), gate-revert even earlier, waiting 30 s for the created-page event (zero user update events delivered in that window); (3) a bisect (control, then each group of the 12 removed, then all 12) delivered a user page update within 4-5 s every time. `forge logs` after the trim: no scope refusal; every 401 is AUTH_TYPE_UNAVAILABLE (a user-context call with no user), the same lines as before the trim.
