## 1. STRATEGY

**The angle: everyone else tracks; Sentinel Vault enforces.** Every incumbent in this category is advisory. Comala (6,104 installs) flips page restrictions per state; AppFox flips permissions and routes cross-space publishing; Breeze routes edits through working copies; SoftComply choreographs versions and permissions; ApprovalFlow and Approval Path pin approvals to versions and flag them stale. None can guarantee an approved page stays byte-identical — the documented audit gap is "a page gets approved, someone makes a 'minor' edit afterward, and the page continues to carry its Approved status" (Flowdence guide, verified). Sentinel Vault already owns the missing half: attachment auto-revert, sealed-section tamper restore, whole-page revert-to-last-good, and structural compare (SV-M7). A workflow layer here means **Approved is a physically enforced state**: any non-privileged edit is reverted (or demotes the state), and structural compare can attest "verified unchanged since approval." Positioning discipline (per the verified competitor nuance): sell **"enforced / reverted"**, never "detected" — detection-by-state-reset and stale-approval flags already exist elsewhere.

Three secondary wedges nobody serves: **section-level workflow** (only AppFox just shipped section approvals; nobody combines approval with section *enforcement* — SV has sealed sections), **attachment lifecycle** (all competitors are page-centric; SV is attachment-native), and **Comala Cloud parity resentment** (weaker automation than DC, no webhooks, no workflow-attach API, 1★ reviews about 3,000× manual JSON copy-paste; Aura already farms switchers). **Honest scoping note:** F1–F7 below are page-level only — the section-level and attachment-lifecycle wedges are deliberately deferred to a follow-up expansion (they need their own candidate specs on top of the F1 engine) and must stay OUT of positioning copy until built; the parity-resentment wedge is the one this expansion actually serves (and only if F1 ships the at-scale application story — see F1). A Forge-native, no-egress, Runs-on-Atlassian app with an opinionated small state set (Draft → In Review → Approved → Expired) also undercuts the #1 Comala complaint: implementation complexity.

**How it composes (core-fit verdict: ~80% of the engine already exists in-repo).** The workflow capsule is a *coordinator* over existing primitives:
- Page state → the `writeValidationState()` content-property pattern (`src/server/capsules/validations/logic.js`) with a **new** property key `sentinel-vault-workflow` (never overload `sentinel-vault-validation` — gate mode and revert reconciliation SV-m2 rewrite it on their own schedule).
- Approvals → clone of the edit-request → approve → grant lifecycle (`src/server/capsules/editreq/actions.js`), re-keyed to `(pageId, stateId, approverAccountId)`.
- Transition conditions → the existing pure `evaluateRules()` (`src/server/infra/rules-engine.js`) plus the `ai-validation-queue` LLM worker.
- Enforcement → the validation revert loop (`src/server/triggers.js:529-570`) pointed at an `approvedVersion` stamped at transition time.
- Review dates → the `expirySweepTask()` pattern (`triggers.js:846`); notifications → bulletins + mention-comments (`bulletins/logic.js`, `infra/notice-composer.js`); per-space assignment → `resolveEffectiveConfig()` fallback pattern (`validations/logic.js`).

**What native Confluence already does — integrate, never duplicate.** (a) **Content statuses** exist natively (colored badge, v1 REST `GET/PUT/DELETE /wiki/rest/api/content/{id}/state`) but gate nothing and emit **no Forge event** — so SV owns the state machine in app-owned storage (Custom Entity Store, F1) and optionally *mirrors* outward to the native chip (F6, spike-gated); externally-set native states are advisory input only. (b) **Versioning** is native — bind approvals to a version number (the gap Atlassian's own automation-approvals article concedes) and use native history as evidence; build no diff storage (SV-M7 covers app-side compare). (c) **Confluence Automation** does soft status-driven approvals but has no API Forge can touch — coexist, don't fight; our pitch is enforcement it cannot do. (d) **Page restrictions** are the only native gate; SV's revert model makes them optional, which sidesteps Comala Cloud's worst behavior (published page hidden from all viewers on re-draft) and the 2026 RBAC transition risk.

**Guardrail summary:** the entire expansion maps onto already-consented scopes (verified against `manifest.yml`, 30 scopes) → **minor version, zero admin re-consent, Runs on Atlassian preserved** (no egress; @forge/llm is Atlassian-hosted). New manifest modules and storage entities are minor-version changes.

### F1 (#42) — Workflow state engine + on-page state chip  *(foundation — everything else depends on it)*
- **End-user:** A page carries a named workflow state (Draft / In Review / Approved / Expired by default; steward-definable per space or globally). The current state shows as a colored chip on the page (doc ribbon) and in the realm console; users with rights move the page between states from the panel; every transition is logged with who/when. Workflows attach **at scale** (table stakes #6): per-space default assignment that auto-applies to existing pages and to new pages on `created:page`, label-filtered assignment (label added/removed events), and bulk apply from the realm console — the direct answer to the Comala "3,000 manual copy-pastes across 300 spaces" 1★ scar the strategy cites; without this the wedge claim is hollow. **Native-chip coexistence:** the native content-status chip (settable by anyone with edit permission) is advisory input only and can disagree with SV state until F6 mirroring is verified and enabled; v1 ships steward guidance in the config UI — disable native suggested statuses in workflow-governed spaces, or enable F6 once it passes its spike — so the two-chips-disagree case is documented and steered, not ignored.
- **Reuses:** config-with-fallback pattern `resolveEffectiveConfig()` (`src/server/capsules/validations/logic.js`, keys `validation-config-global` / `validation-config-space-{sanitizedKey}`, same `sanitize()` regex); content-property state pattern `writeValidationState()` (same file); steward gating `authorizeSteward()` (`src/server/shared/steward-checks.js`); capsule registration like the other ten spreads (`src/server/registry.js`); doc-ribbon 5s poll + `check-seal-stamp` pattern for chip refresh; transition-log storage modeled on `storeFindings()` key shape (`ai-finding-{pageId}-{ts}`) but **without its TTL** (see data model); at-scale assignment listens to `avi:confluence:created:page` + label added/removed events (GA, scopes held — forge-feasibility §2).
- **New data model:** config in KVS: `workflow-def-global` / `workflow-def-space-{sanitizedKey}` = `{ enabled, workflows: [{ id, name, states: [{ id, name, color, final?, enforce?, reviewAfterDays? }], transitions: [{ from, to, conditions: rules[], approvals: [] }] }], assignment: { spaceDefault?, labelFilters? } }`. Page state is a **Custom Entity Store entity from day one** — `workflowState` (pageId, spaceKey, workflowId, stateId, enteredAt, enteredBy, approvedVersion?, reviewDueAt?) with secondary indexes `by-state`, `by-due-date`, `by-space` (GA; manifest entity addition = minor version). This decision is made HERE, not in F7: populated indexes are hard to migrate (forge-feasibility §5), and F3's integrity sweep, F4's review sweep, and F7's dashboard all query these indexes — shipping F1 on plain KVS keys would force exactly the migration the platform docs warn about. `workflow-log-{pageId}-{ts}` transition/approval log with **NO TTL** — this history is the compliance artifact the strategy sells (Comala's DC→Cloud loss of workflow history is a top documented switcher grievance; a self-deleting audit trail is disqualifying for the ISO buyers being targeted); retention is indefinite, exportable via F7's CSV, deletable only by an explicit steward purge tool. Content property `sentinel-vault-workflow` = `{ workflowId, stateId, enteredAt }` (CQL-discoverable + cheap trigger probe); optional `workflow-last-modified` stamp mirroring `protections-last-modified`.
- **Resolvers:** `load-workflow-config`, `store-workflow-config` (steward), `get-page-workflow`, `assign-workflow`, `bulk-assign-workflow` (steward), `request-transition`, `force-transition` (steward), `get-workflow-log`.
- **Forge capability:** existing resolvers + `confluence:pageBanner` (GA, already in manifest as `doc-ribbon`); optional `confluence:contentBylineItem` (GA; static variant only — the dynamic/contentPropertyKey variant is Preview-adjacent, skip in v1). Custom Entity Store (`app.storage.entities`, GA); KVS `storage:app` (held).
- **Scores:** Effort 4 (new capsule + config UI + at-scale assignment listeners + entity-store setup; every piece is still transcription of an existing pattern, but the surface grew). Impact 5 (unlocks the whole category; without states SV isn't evaluated). Risk 2 (pure-additive keys/entities; the one trap — property-key separation from `sentinel-vault-validation` — is understood and cited).

### F3 (#44) — Enforced Approved state (seal-on-approve, revert-on-tamper)  *(the differentiator)*
- **End-user:** When a page enters a state marked `enforce` (typically Approved), Sentinel Vault records the exact page version. Any later edit by a non-approver/non-steward is automatically reverted to the approved version (or, in "demote" mode, drops the page back to Draft with a banner + comment explaining why). **Claim discipline:** sell "tampering is reverted within minutes and attested by structural compare" — NOT "the badge can never lie" (between tamper and revert the badge is briefly wrong; a dropped event or failed write would otherwise leave it wrong indefinitely, which is why the integrity sweep below is part of this feature, not optional hardening). And do not print "no competitor can do this" in outward copy until SoftComply's approve-lock is verified in-product: their "once approved, locked, cannot be modified" is vendor-stated, and "choreography, not tamper-revert" is our own inference (competitors.md §4) — the honest verified claim is that no competitor *documents* live-page tamper-revert.
- **Reuses:** the validation revert machinery wholesale — `runValidationPhase()` revert mode (`src/server/triggers.js:529-570`), `getLastGoodVersion()/setLastGoodVersion()` shape (store our own `approvedVersion` on the `workflowState` entity instead), SV-M1 concurrency guard (`triggers.js:539` — abort if version moved since evaluation), SV-M2 (never announce "restored" unless the write succeeded), ignore-own-writes guard `resolveAppAccountId()` fail-closed check (`triggers.js:114-124`, SV-M3); the enforcement decision runs off a cheap `sentinel-vault-workflow` property probe (early-bail probe pattern from `collectSectionSealsForPage()`, `triggers.js:328`) — see who-wins below for where it sits in the pipeline.
- **Who-wins semantics (decided here, not left to the harness):** while a page is in an enforced state, **the approver set is privileged over sealed-section owners**. The workflow probe runs FIRST in `pageContentTrigger`, before the section pass: if the page is enforced and the editor is not an approver/steward, the pipeline short-circuits to the whole-page revert to `approvedVersion` and the SV-M5 owner re-baseline (`triggers.js:370-387`) is **suppressed for that event**. Without this rule, a sealed-section owner who is not an approver edits their section → the section pass re-baselines the snapshot to the new content → the workflow pass reverts the whole page to version N → snapshot and body permanently disagree and the two subsystems ping-pong on every subsequent event. A seal owner who needs to edit their section on an Approved page must first transition it out of Approved (`request-transition`); the revert notice says exactly that. Approver/steward edits skip enforcement and fall through to the normal section → media → validation passes (their edits re-baseline as today). Single-writer discipline holds: the enforced-revert IS the event's one write.
- **New data model:** `workflow-integrity-notified-{pageId}` dedup flag for the **approved-version integrity sweep** — a new `workflowSweep` scheduled function (idempotent; scans enforced pages via the F1 `by-state` entity index) compares the current page version against `approvedVersion` and re-runs enforcement on any drift. This is the backstop for dropped/late `updated:page` events (ECO-1403 history) and failed revert writes (SV-M2 anticipates them): without it, a single missed event leaves the badge wrong indefinitely. F4's review-date pass later joins this same scheduled function. Otherwise none beyond F1 (`approvedVersion` field + log entries). Explicitly does NOT create synthetic section seals and never touches `section-snapshot-*`, `section-protection-*` `contentHash`, or `protection-*` `sealedVersion` — re-baseline semantics (SV-M5) belong to sealing flows only; F3 only *suppresses* the re-baseline while enforced, it never rewrites seal data.
- **Forge capability:** `avi:confluence:updated:page` trigger (GA, subscribed already). Platform caution: this event was the subject of ECO-1403 (high latency / out-of-order delivery; now Closed-Done) — measure current latency in the harness before promising near-real-time revert; the SV-M1 version guard is the correctness backstop either way.
- **Scores:** Effort 4 (small diff but inside the most delicate file in the repo, plus the sweep). Impact 5 (the entire competitive moat — "enforced, not tracked"). Risk 4 (**low confidence flagged honestly**: the who-wins rule above is the design answer to the hazard the pipeline comment at `triggers.js:93-102` warns about, but probe-first short-circuit + SV-M5 suppression is exactly the kind of subtle pipeline surgery where a wrong branch destroys user content — it needs harness proof, not pattern-following; single-writer discipline: mutate shared `ctx.adfDoc` / one revert write, never a second `writeDocBody()`).
- **Guardrails:** no new scope; one `scheduledTrigger` manifest module addition for `workflowSweep` (minor version; app currently runs three — verify platform per-app limit at build time); no Preview API. Requires dedicated forge-live-harness scenarios before it ships: tamper-while-approved; approver edit; seal-owner edits own section while page is Approved (SV-M5 suppression path — assert no ping-pong across two subsequent events); concurrent seal restore + workflow revert on one event; integrity sweep catches a synthetically-missed event and a failed revert write.
- **Ledger row:** `| 44 | Enforced Approved state (revert-on-tamper) | Backend → ribbon/comments | discovered | 1 | 1 | 1 | 1 | 1 | 19.0 | — |`

### F4 (#45) — Review dates & automatic expiry transitions
- **End-user:** Entering a state can start a review clock (`reviewAfterDays`, steward-configurable per space). When the date passes, the page automatically transitions to the configured destination (e.g. Approved → Expired), the chip changes, and owners/watchers get a reminder notice — with escalating reminders before the deadline. Closes the "review-date loop with teeth" that Midori only notifies on.
- **Reuses:** `expirySweepTask()` shape exactly (`src/server/triggers.js:846` — sweep, compare due date, dedup flag); ships as a second pass inside the `workflowSweep` scheduled function introduced in F3 (integrity pass), querying the F1 `by-due-date` entity index instead of a key-prefix scan; the harness-drivable `invoke(expirySweep)` test hook (commit 74a0911) extends to `invoke(workflowSweep)`; notices via bulletins/notice-blueprints as in F2; bounded cursor discipline for queries.
- **New data model:** `workflow-review-notified-{pageId}` dedup flag; `reviewDueAt` already on the `workflowState` entity (F1).
- **Forge capability:** `scheduledTrigger` (GA; `hour`/`day` intervals, no cron; failed runs not retried, duplicates possible → sweep must be idempotent — the existing sweep already is). Stays a **separate scheduled function from `expirySweepTask`** (that sweep already iterates all `protection-*` against a 25 s budget); sharing `workflowSweep` with F3's integrity pass is fine — both are index-driven and cheap.
- **Scores:** Effort 2 (near-transcription of existing sweep + one transition call). Impact 4 (one of the five must-build table stakes; the "expiry with teeth" wedge). Risk 2 (idempotency and dedup patterns proven in-repo; drifted timing is acceptable for daily semantics).
- **Guardrails:** no new scope; no new manifest module (the `workflowSweep` scheduledTrigger ships with F3); no Preview API.

### F5 (#46) — Transition conditions: structural rules + AI review gate  *(DEFERRED — ships last, and only on a demand signal)*
- **End-user:** A transition can require conditions before it's allowed: structural rules ("has label X", "required heading/table/macro present", length bounds) evaluated instantly, and optionally a Semantic AI review ("no unresolved risky changes vs last approved version") that runs asynchronously and blocks the transition until it lands — with AI diff-summary at approval time ("what changed since last approved") as reviewer aid. No competitor offers semantic gating, and it stays egress-free.
- **Reuses:** `evaluateRules(adfDoc, pageLabels, rules)` (`src/server/infra/rules-engine.js` — pure, no I/O; conditions field IS a `rules[]` array in the exact existing schema); AI path = `enqueuePageValidation` → `ai-validation-queue` → `ai-worker.js` → `storeFindings()` / `ai-latest-{pageId}` (`validations/logic.js`); version compare for diff-summary uses v2 `GET /wiki/api/v2/pages/{id}/versions` (scope held) + SV-M7 structural compare.
- **New data model:** transition request gains `{ pendingChecks: [{ type: ai, jobId, enqueuedAt, timeoutAt, onTimeout: block|pass }] }` on a `workflow-transition-pending-{pageId}` key; mandatory timeout + fallback rule so a stuck job cannot wedge a transition.
- **Forge capability:** `@forge/events` queues (GA; at-least-once, retries within retention window — the existing two queue+consumer pairs prove the pattern); `@forge/llm` (**Preview**, production-permitted, Atlassian-hosted so Runs-on-Atlassian-safe; usage bills to the developer since June 2026 → AI conditions must be opt-in per space).
- **Demand honesty (why deferred):** the sole research justification is competitors.md gap #6 — "nobody in this space offers semantic checks" — which is an absence of *supply*, not evidence of *demand*. Not one user review, community thread, or complaint in comala.md/competitors.md asks for AI-gated transitions, while Comala's #1 documented complaint is complexity for non-technical teams and SV's own wedge is the opinionated simple state set. The structural-rules half (pure `evaluateRules()`, instant, no AI) is safe and can ship with the engine if trivially cheap at build time; the async AI gate waits for a concrete pull (customer ask, trial feedback, discovery interview) before any build.
- **Scores:** Effort 3 (rules path is direct reuse; the async pending-check state machine is the new work). Impact 4 (unique differentiator #2 *if* demand materializes — impact currently unevidenced). Risk 4 (**low confidence flagged honestly**: "block a transition until an async job lands" has no precedent in-repo — the existing queue flow is manual-first fire-and-poll; the pending/timeout/fallback machine is new surface where subtle wedges hide; also LLM cost exposure and Preview-API dependency stacking on one feature).
- **Guardrails:** no new scope, no new module (`llm` module + queues already declared); **Preview API in the path (@forge/llm — already accepted in-app)**; developer-billed LLM cost (see §4); **demand-evidence gate before build**.
- **Ledger row:** `| 46 | Transition conditions (rules + AI gate) | Backend + realm console config | discovered | 1 | 1 | 1 | 1 | 1 | 17.0 | — |`

### F6 (#47) — Native content-state mirroring  *(BUILD-GATED on a live API spike — feasibility asserted, not verified)*
- **End-user:** When Sentinel Vault changes a page's workflow state, the native Confluence status chip (visible in the editor, page header, and native search/filters) updates to match — SV state is visible everywhere Confluence shows statuses, with zero extra UI. Default **off** per space (see §4). This is also the resolution for the two-chips-disagree problem F1 documents.
- **Mandatory pre-build spike (live tenant):** the design currently assumes an asApp PUT can set arbitrary named states — native.md says otherwise where it's testable: (i) a state PUT **fails if custom states are disabled in the space and the name isn't one of the ≤5 admin-defined suggested statuses** — in those spaces the mirror degrades to "works only if the space admin pre-creates matching suggested names", a materially different feature; (ii) where custom states ARE allowed, custom statuses are **per-user** — whose "personal" state an asApp PUT creates and whether other users even see it is untested; (iii) Confluence Automation has a first-class "Content status changed" trigger and Standard tenants get **100 executions/month/instance** — whether an app-authored PUT fires tenant Automation rules is unverified either way, and if it does, every SV transition burns customer quota and can cascade (Automation edits page → SV enforcement reacts → transition → mirror PUT → Automation again). The spike must answer all three before any build; (i)/(ii) shape the stateMap design, (iii) decides whether default-off is a preference or a hard requirement.
- **Reuses:** transition side-effect hook in the F1 engine; ignore-own-writes guard (`triggers.js:114-124`) — the mirroring PUT publishes a new page version and re-fires `updated:page`, which the app-account check already absorbs.
- **Single-writer discipline (core-fit invariant #2):** the mirror PUT **never runs inside `pageContentTrigger`**. Resolver-driven transitions may call it inline (outside the event pipeline); transitions initiated by trigger passes (F3 demote mode, F4/F3 sweep) enqueue the mirror as an async `@forge/events` job — a state-publishing PUT fired mid-pipeline would be a second independent publish for the same event, and nothing like SV-M1 guards the state PUT against a concurrent user edit racing it. Drift re-asserts are debounced: default is notice-only; when re-assert is enabled, at most one re-assert PUT per page per sweep interval.
- **New data model:** `{ mirrorNativeState: bool, stateMap: { stateId → nativeStateName/color } }` inside `workflow-def-*` (F1); stateMap entries are validated against the space's suggested statuses at config time when custom states are disabled (feature-detect via `GET /space/{key}/state/settings`). Drift rule: native chip changed by a user ≠ workflow transition; detect on `updated:page` probe / sweep and surface a notice (re-assert only per the debounce above; app-owned state is authoritative — no native state-change event exists for apps).
- **Forge capability:** REST **v1-only** content-states API (`PUT /wiki/rest/api/content/{id}/state` — sets state AND publishes a version; `GET .../state`, `GET /space/{key}/state/settings` for feature-detection per space; no v2 equivalent as of July 2026 and not on the active removal list). Scope `write:confluence-content` (held). Isolate behind an adapter for eventual v2 migration.
- **Scores:** Effort 3 (adapter + toggle + drift probe + async side-effect job + the spike). Impact 3 (strong visibility/credibility win; not functionally load-bearing). Risk 4 (**feasibility unverified — see spike**; v1-only surface; PUT-publishes-version churn interacts with `approvedVersion` bookkeeping — mirror BEFORE stamping `approvedVersion`, or stamp the post-mirror version; Automation quota/cascade exposure; feature availability varies per tenant/space → must feature-detect, never assume).
- **Guardrails:** no new scope, no new module, no Preview API (v1 REST is GA-supported); **build-gated on the spike**.
- **Ledger row:** `| 47 | Native content-state mirroring | Backend → native status chip | discovered | 1 | 1 | 1 | 1 | 1 | 14.0 | — |`

## 3. EXPLICIT NON-GOALS

1. **Rebuilding the native content-statuses feature, or treating the native chip as authoritative** — native duplication. Honest scoping (this non-goal was previously worded so broadly it contradicted F1): SV *does* ship its own state chip, because native statuses can be neither the state store nor the sole display — they gate nothing, are feature-gated per tenant/space, are settable by anyone with edit permission, and emit no Forge event. What we will NOT build: suggested-status management, per-user custom-status UI, or any state machine keyed off the native chip. Native states are advisory input only; visibility inside native UI/search comes from mirroring into them (F6, once spike-verified), not from rebuilding them. Until mirroring is on, the two chips can disagree — F1 documents this and ships steward guidance (disable native suggested statuses in workflow-governed spaces, or enable F6).
2. **Any SMTP/external email or webhook egress for notifications** — egress risk; instantly forfeits Runs on Atlassian. All notifications stay Confluence mention-comments, watchers, bulletins, and app surfaces (there is no public Confluence Cloud "send notification" REST API anyway).
3. **External (non-licensed) email approvers** (Approval Path's differentiator) — requires egress + unauthenticated action links; same badge-forfeiting reason.
4. **Our own diff/version storage** — native duplication. Confluence versions + native compare UI are the evidence trail; approvals pin version numbers; SV-M7 structural compare covers app-side integrity checks.
5. **A workflow authoring language or full visual workflow builder (Comala-style JSON/markup editor)** — effort/risk, and it rebuilds the incumbent's #1 complaint (complexity for non-technical teams). We ship an opinionated small state set with steward-editable parameters; arbitrary user-defined state machines are out for this expansion.
6. **Cross-space draft→publish publishing (Comala Publishing two-space model)** — effort/risk and a separate product's problem; our enforcement model makes it unnecessary (viewers keep seeing the approved content because tampering is reverted, which beats Comala Cloud's hide-the-page behavior without any space choreography).
7. **Page-restriction flipping as the primary enforcement mechanism** — native-model risk: it's the coarse mechanism behind Comala Cloud's worst UX, the restrictions API is v1-only, and the 2026 RBAC transition makes the surface unstable. Enforcement is revert-based; restrictions at most a later optional add-on.
8. **Integration with Confluence Automation rules** — impossible, not just avoided: Forge apps cannot read/create/trigger native Automation rules (no API). Coexist; document the difference.
9. **E-signatures / OTP (21 CFR Part 11 positioning)** — effort/risk: legal-compliance claims need dedicated diligence; SoftComply owns that niche at 120 installs. Revisit only with a regulated-customer pull. **Positioning discipline while this holds:** every serious competitor in the regulated segment ships a signature/MFA story (Comala OTP, AppFox MFA/2FA, SoftComply Part 11, Phase Locked 2FA) and compliance-evaluation checklists ask for signatures on approval decisions — our answer is "no". Outward copy therefore sells tamper-evident integrity attestation ("verified unchanged since approval") as a *complement* to an audit program, and must not claim ISO/Part 11 compliance-evaluation readiness.
10. **Read confirmations** — adjacent category (Comala ships it as a separate app); out of scope for the workflow expansion.
11. **Inline-task-based review assignments** — no clean public create API for inline tasks; treat as unavailable (per forge-feasibility §9).
12. **Blog posts and live-doc-specific workflow parity in v1** — pages first; blog events exist but every workflow surface/test doubles. Revisit after 42–45 are verified.

## 4. OPEN GUARDRAIL QUESTIONS (beyond pre-authorized scope/major-version changes)

Scope additions and major-version bumps on DEV are pre-authorized — and, notably, **this expansion needs neither** (zero new scopes, minor-version only, verified against `manifest.yml`). Two items remain that the pre-authorization does not cover:

1. **LLM spend posture for AI transition conditions (F5/#46).** @forge/llm usage is billed to the app developer and counts toward the Forge monthly bill since June 1, 2026. AI-gated transitions can fire on every transition attempt in a busy space — materially more volume than today's manual-first AI review. Proposed default: AI conditions **off by default, opt-in per space, with a per-space daily cap**. Question for the owner: confirm this default, or set a different cost ceiling before F5 is built.
2. **Version churn from native state mirroring (F6/#47).** The native content-state PUT publishes a new page version on every transition — page history fills with app-authored versions, visible to end users, and it interacts with `approvedVersion` bookkeeping. Proposed default: mirroring **off by default per space**, and when enabled the engine stamps `approvedVersion` from the post-mirror version. Not blocking if the default is accepted; flagging because it permanently alters user-visible page history, which is beyond a DEV-environment concern once this ships outward.
3. **Native-mirror interaction with customer Automation rules and quotas (F6/#47).** Confluence Automation has a first-class "Content status changed" trigger, automation loops are a documented failure mode, and Standard tenants get **100 executions/month per instance**. Whether an app-authored state PUT fires tenant Automation rules is unverified either way — if it does, every SV transition consumes customer quota and can cascade with status-driven rules (Automation edits page → SV enforcement → transition → mirror PUT → Automation again). The F6 pre-build spike must test this on a live tenant with an Automation rule armed; if confirmed, default-off becomes a hard requirement (not a preference), the drift re-assert stays notice-only, and the mirroring docs must warn admins explicitly.

Nothing else blocks: no Preview API is newly adopted (@forge/llm is already declared and in production use in-app), no CSP/remotes/egress changes, no admin re-consent, Runs on Atlassian retained throughout.
