## MANDATORY rules (owner-set — no exceptions)

- **LIVE-BROWSER VERIFY every UI change (owner directive it26) — the mock screenshot harness is NOT enough.** After a UI/frontend change: `forge deploy -e development` → **`forge install --upgrade --non-interactive -e development --site wolfaenpak.atlassian.net --product Confluence`** → run the **DEEP** browser spec in `~/Projects/forge-live-harness` (`RUN_ID=sv-deep npx playwright test scenarios/sentinel-vault/realm-console-deep.spec.ts --project=chromium`; shared `.auth/profile` session, same wolfaenpak instance as lz-ppm — no separate auth) → **Read the evidence PNGs** (`evidence/<RUN_ID>/…/steps/*.png`) to see the ACTUAL deployed UI in real Confluence. NOTE: the plain `realm.spec.ts`/`admin-render.spec.ts` render smokes are SHALLOW — they only assert "not blank", so a SPINNER passes them (that's why the it26 hang slipped through). The DEEP spec (`realm-console-deep.spec.ts`, added it26) is the real check: it enters the iframe with `readySelector: ".space-admin-title"` (a spinner can't match it → FAILS on a stuck-loading hang), then clicks EVERY tab and asserts each renders real content (no blank/error/spinner) + screenshots each. Extend it (or add a sibling deep spec) when a UI change needs a specific interaction verified live; a steward-console deep spec is a good next addition. The mock harness renders the *built* bundle with instant mock data; it CANNOT catch: (a) stuck-loading hangs (real resolvers that hang/slow — it26 found the realm-console hung forever awaiting `enumerate-operators`), (b) DEPLOY STALENESS (see below), (c) real-Confluence render/integration failures. If the render smoke only catches a transient loading state, add a longer-wait diagnostic spec (poll the iframe, or `page.waitForTimeout(22000)` + fullPage screenshot).
- **`forge deploy` ALONE does NOT update the served frontend — the dev INSTALL can be stuck at an old version.** it26: `forge install list` showed the dev install (`09797ffe-…`) frozen at **App version 5 / "Outdated app"** while I'd deployed v6.16.0 — so EVERY UI change since the 5→6 major bump (the D8 scope removal) was built + "deployed" but NEVER live (backend/resolvers DO update on deploy — that's why the grade E2E passed — but the install's frontend resources are frozen until upgrade). ALWAYS run `forge install --upgrade` after deploying and re-verify in the browser. A green mock screenshot + a green grade can BOTH pass while the live UI is stale.


- **Qualitative UX review on EVERY UI change** (owner directive — the CogniRunner lesson): passing tests + a11y + code-review is NOT enough. In the verify phase of any UI iteration, render the change in context (light+dark), LOOK at it as a naive user, AND spawn a fresh-eyes "naive user" reviewer over the screenshots asking "does this make sense? is anything confusing/cluttered? is it usable end-to-end from the UI?". Act on genuine confusion (rename, disambiguate, remove clutter, defer half-built surfaces) — do NOT add motion/polish for its own sake; restraint (removing/simplifying) is often the right tweak. A green loop that quietly makes the app more confusing is the failure mode to avoid.

- **Git identity**: every commit uses `leanzero-srl <office@leanzero.net>` as BOTH author AND committer (set `GIT_AUTHOR_*` and `GIT_COMMITTER_*` env vars per command; never edit git config). NO `Co-Authored-By` trailers. Verify with `git log -1 --format=fuller`.
- **UI hard rules**: no left accent rails/stripes ever; no faded/washed tints — solid saturated accents only; no native browser primitives (alert/confirm/prompt/`<select>`) — use the app's own dialog/dropdown primitives; avoid the AI-default looks (cream+serif+terracotta `#D97757`, near-black+acid-green, broadsheet hairlines).
- **Core contract is inviolable** (reference/CORE_CONTRACT.md): change around it, never through it. Adapters over rewrites.
- **AQL invariants**: WIP=1; evidence over vibes (live harness run before "verified"); adversarial pass on research, design, and verification; small reviewable diffs; ledger updated every phase.
- Loop never touches the production environment/install.
- **New functionality gets a REST route, in the same iteration, not a follow-up.** Set 2026-09-15 (owner instruction, after a demo build found the app had real features — sealing, realm config, workflow, classification — reachable only through the Confluence UI, with no way to script or migrate them). Any new capsule/action lands its REST surface — through `config-api` if it's a write, or a documented Confluence-properties read path if it's a read — in the SAME tick it ships, never parked. Before calling an iteration done, ask: "could a script drive this without opening Confluence?" — if the honest answer is no, name the reason in the changelog or go back and add the route.
