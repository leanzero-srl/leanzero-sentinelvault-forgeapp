# Iteration 3 — #42 Per-space workflow settings + auto-assign-on-create

Branch: `aql/workflow-state-engine`. Feature: ledger #42, the at-scale-assignment (backend) half — new pages in an enabled space automatically get a workflow (the Comala "no bulk apply / 3,000 copy-pastes" pain, for new content).

## Workflow plan (dynamic)
Backend capability slice. Research (done): the page trigger already subscribes `avi:confluence:created:page` (no manifest change); the validation phase already resolves spaceKey from the event and runs as an independent pass — auto-assign mirrors it. Verify: unit tests + a live E2E that creates a real page and asserts the trigger auto-assigns it + full grade + an adversarial trigger-safety review (core-touching → hardest scrutiny).

## Decision & spec
- **Functional change:** a steward can enable "document workflow" for a space with "auto-assign new pages"; thereafter any page created (or first edited) in that space with no workflow gets the space's workflow assigned automatically, at its initial state, logged as "auto-assigned on create".
- **Scope boundary:** this iteration is the BACKEND mechanism + a live E2E. The steward config UI to toggle it (realm-console tab) = iteration 4; bulk retro-apply to *existing* pages = deferred (ships with the UI button that drives it). Deliberate: keeps the risky trigger change isolated and fully harness-verified before wrapping UI around it.
- **Data model:** `workflow-settings-{sanitizedKey}` = `{ enabled, autoAssignNew, workflowId }` (default all-off). New logic: `getSpaceWorkflowSettings`/`setSpaceWorkflowSettings`, pure `shouldAutoAssign(settings, hasWorkflow)`, and `autoAssignOnEvent({pageId,spaceKey,actor})` (idempotent orchestration). `assignPageWorkflow` gained an optional `logReason`.
- **Trigger hook:** a new independent try/catch pass at the end of `pageContentTrigger` (after `runValidationPhase`), resolving spaceKey the same way the validation phase does, calling `autoAssignOnEvent`. Runs only for non-app actors (the app-account early-return at triggers.js ~122 guards both this and the validation phase).
- **Core contract preserved:** purely additive. **No loop:** auto-assign's only page-facing write is the `sentinel-vault-workflow` content property via `writeStateContentProp` — content-property writes do NOT fire `updated:page` (proven by the existing `writeSealContentProp` doing the same from this trigger). **Idempotent:** assigns only when the page has no workflow, so a re-fire / subsequent update no-ops. **Cheap for non-enabled spaces:** one KVS get, then early return. Exceptions swallowed so the seal passes are unaffected.

## Design-critic pass (adversarial self-review)
- *"Runs on every update, not just create — wasteful."* → For non-enabled spaces it's ONE KVS get then return; for enabled spaces it's a second get (readPageWorkflow) then no-op once assigned. Acceptable; keying off "has no workflow" is simpler and safer than trusting a created-vs-updated event flag, and self-heals pages created while the space was disabled.
- *"Enabling a space auto-assigns to test pages from other suites."* → The E2E always disables the space setting in `finally` (deletes `workflow-settings-{key}`) so it can't leak.
- *"Trigger file is the most delicate — risk."* → The pass is isolated (own try/catch, own KVS keys), touches no seal/section/validation/media state, and mirrors the proven independent validation phase. Flagged for the adversarial trigger-safety review (below).

## Verify (live)
- Unit 30/30. Deploy clean. **Full grade PASS** (units 90/90, workflow-e2e 13/13, **workflow-autoassign-e2e 8/8**, live-trigger 8/8, seal-e2e 4/4, forge-logs clean) — trigger change, zero regression.
- workflow-autoassign-e2e proved LIVE: enable space → create a real page → the `created:page` trigger auto-assigns the default workflow (draft), writes the content property + log ("auto-assigned on create"); an update does NOT re-assign (idempotent, still one log entry); cleanup disables the space setting.
- Adversarial trigger-safety review (9 agents, 3 lenses): **loop-safety CLEAN** (the no-loop reasoning held), 4 findings CONFIRMED (2 distinct issues), 2 correctly rejected. Both real issues fixed + re-verified:
  - **Concurrency (MEDIUM):** `autoAssignOnEvent` was check-then-act with no dedup marker → a duplicate/concurrent `created` delivery could double-append to the no-TTL compliance log (primary record converges, but the log is the capability's compliance selling point). Fixed with a one-shot `workflow-autoassigned-{pageId}` claim marker before the assign, mirroring the `markVersionChecked`-before-side-effects pattern the contract (T6/SV-m1) already mandates. KVS has no CAS, so this narrows the window to a single get→set — the same residual the validation phase accepts.
  - **Ran on updates + mislabeled (LOW):** the pass fired on `updated:page` too, logging edits as "auto-assigned on create." Gated to `event.eventType.includes("created")` — now `autoAssignNew` means exactly new pages and the log reason is always accurate. Existing-page backfill is deferred to the explicit bulk-apply (iteration 4).
  - **Rejected (correctly):** the "unconditional KVS get on the hot trigger" (a point-get is within CORE_CONTRACT T4's budget, which is scoped to seal passes and blesses the heavier validation body-read) and "null-spaceKey silently skipped" (fail-safe, mirrors the proven validation phase).

- **Score delta (#42):** no axis change (backend capability; the user-visible axes moved in iteration 2). Fn stays 4; the config UI (iteration 4) is what flips #42 to fully verified.
- **Remaining #42 sub-slice (→ iteration 4):** steward config UI (realm-console "Workflow" tab) to toggle enable/auto-assign — researched: mirror `ValidationsEditor` as a `WorkflowSettingsEditor` kit, mount as a steward tab (userRole-gated, spaceKey=realmKey) exactly like the Validations tab. Plus bulk retro-apply to existing pages (driven by the UI button).
- **Skill learnings:** (1) any trigger-file pass that writes a no-TTL/compliance record MUST claim a dedup marker BEFORE side effects (T6 pattern) — check-then-act on a late-written record leaves a concurrent double-fire window; Forge events are at-least-once. (2) Gate event-type-specific behavior on `event.eventType` (destructured in the artifact trigger) — don't assume a shared page handler is create-only. (3) The 3-lens trigger review (loop / ordering / concurrency) is the right shape for any triggers.js change and should be a saved recipe for #44's enforcement work (the same file, higher stakes).
